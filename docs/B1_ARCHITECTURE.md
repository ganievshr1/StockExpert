# Архитектура StockExpert для многопользовательской проверки B1

Выпуск сохраняет существующие входы и выходы: Excel остатков, файл потребности, нормализованные паспорта, подбор и прежние отчёты. Добавлены две конфигурации очередей и отдельный раздел проверки B1. Разделение очередей — проверяемое изменение, а уменьшение p95 на 30% — критерий эксперимента, не гарантированное свойство кода.

## Обычный путь данных

1. React отправляет запросы через Nginx `/api/` в FastAPI. JWT определяет пользователя и его организацию.
2. Сессия, документы, позиции и задания сохраняются в PostgreSQL. Исходные файлы лежат в MinIO. У каждой сессии и каждого задания свой UUID; данные поиска фильтруются по сессии.
3. API фиксирует `Job` со статусом `QUEUED`. Эта запись служит устойчивым реестром ожидающей работы. Ответ о постановке в очередь не означает готовый результат.
4. Celery beat вызывает диспетчер в очереди `control`. Диспетчер публикует задания в Redis согласно `JOB_ROUTING_MODE`.
5. Исполнитель получает блокировку сессии, выполняет подготовку, нормализацию или подбор, записывает состояния и длительности. Матчинг использует Qdrant, BM25, правила признаков и опциональный CPU reranker. Ollama обслуживает локальную генерацию и эмбеддинги.
6. Клиент получает статус и результаты. B1 считает полный клиентский интервал до чтения результата, а не только время ответа о принятии задания.

## Сравниваемые конфигурации

| Параметр | Baseline `shared` | Вариант `split` |
|---|---|---|
| Очереди бизнес-заданий | `shared` | `interactive`, `batch` |
| Сервис `worker` | Один слот общей очереди | Один интерактивный слот |
| Сервис `worker-batch` | Один слот общей очереди | Один пакетный слот |
| Всего бизнес-слотов | 2 | 2 |
| Лимиты бизнес-исполнителей | По 1 CPU и 3 GiB RAM на сервис | Те же ограничения |
| Prefetch | 1 | 1 |
| Управляющий исполнитель | Отдельный `worker-control` | Такой же |
| Контроллер эксперимента | Отдельный `worker-b1` | Такой же |
| Ollama | Общая служба, `OLLAMA_NUM_PARALLEL=1` | Та же служба и тот же лимит |

В split `match` направляется в `interactive`. Полный запуск с готовой повторно используемой базой также относится к интерактивному пути; подготовка каталога и другие пакетные задания направляются в `batch`. Точное правило находится в `app/services/job_routing.py`.

`worker-regex` и `worker-laboratory` сохраняют прежние лабораторные функции. Во время измерения B1 эти эксперименты не запускаются: они используют CPU или общую модель и исказят сравнение. Контроллер B1 не занимает бизнес-слот и не выполняет подбор вместо штатного API.

## Путь проверки B1

Вкладка **Для разработчика → Проверка гипотезы B1** вызывает `app/api/b1_experiments.py`. Контроллер `app/services/b1_experiments.py` создаёт тестовые учётные записи и изолированные сессии текущей организации, затем выполняет реальные HTTP-запросы к обычным маршрутам подбора.

Подготовка тестовых аккаунтов, копий готовой базы и паспортов потребностей происходит до измеряемого окна. Это отдельные подготовительные затраты. Полная серия использует ограниченный пул сессий: занятая сессия не получает второй одновременный запуск. Если генератор не смог отправить запланированный запрос, пропуск сохраняется и прогон не считается валидным подтверждением B1.

Сырые события и сводки хранятся в `/data/b1` в постоянном Docker volume `b1_artifacts`, доступном API и `worker-b1`. Во время исполнения результаты создаются в штатных таблицах PostgreSQL. Между прогонами объёмные строки результатов тестовых сессий B1 архивируются и освобождаются; в экспорте остаются полученная выдача кандидатов и контрольные суммы, в БД — задания, аудит и времена. Прежние пользовательские сессии не очищаются.

Контроллер не перезапускает Docker и не изменяет число исполнителей. Между этапами кампании пользователь переключает compose-конфигурацию и нажимает продолжение. Переключение разрешено после завершения активной работы.

## Доступ и совместная работа

Сохраняется политика исходного проекта: данные доступны уполномоченным пользователям своей организации, а не только автору каждой сессии. Разные организации изолированы. Раздельные тестовые аккаунты и сессии предотвращают смешивание состояния подбора, но не вводят новую модель приватности внутри организации. Раздел B1 доступен администратору.

Общая база представляет склад организации. Операции «использовать позицию» и очистка базы влияют на связанные сессии; во время эксперимента такие изменения не выполняются. Готовая база и набор потребностей фиксируются до начала пары.

## Дополнительные исправления конкурентной работы

- Два первых исполнителя могут одновременно увидеть отсутствие Qdrant-коллекции. Конфликт её создания допускается только при совместимой конфигурации векторов; прочие ошибки остаются ошибками.
- Подбор не выгружает общую Ollama-модель после работы отдельного пользователя. Управление резидентностью оставлено Ollama, чтобы одна сессия не мешала нормализации другой.
- Очереди, время публикации, старт и завершение фиксируются в данных задания. Ожидание и вычисление показываются раздельно.

## Границы архитектурного вывода

Отдельная очередь не создаёт дополнительную GPU. Если обе операции ограничены одной моделью или GPU, выигрыш p95 может отсутствовать. При свободной общей очереди разделение также может уменьшить доступный параллелизм подборов. Если каталог готов и фоновой работы нет, два коротких сценария оценивают конкурентность и время серии, но сами по себе не проверяют гипотезу о конкуренции с подготовкой каталога.
