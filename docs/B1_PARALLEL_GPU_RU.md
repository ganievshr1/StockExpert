# StockExpert 3.9.13-b1.2: один пользователь, десять одновременных запросов

## Что изменилось

В разделе «Проверка гипотезы B1» появился отдельный сценарий
«1 пользователь × 10 запросов одновременно». Одна тестовая учётная запись
отправляет десять запросов без ожидания предыдущего результата. Для запросов
используются отдельные сессии; исходная база и потребности сохраняются.
Существующие последовательный сценарий и сценарий с десятью учётными записями остаются.

Одновременная отправка не равна десятикратному ускорению. Очередь Redis/Celery
сохраняет принятые задания, а worker берёт несколько заданий одновременно.
Новая конфигурация использует один процесс с несколькими потоками:
по умолчанию четыре, при явном выборе — до десяти.
Операции HTTP/БД и этапы разных подборов могут перекрываться. Чистый Python-код
не получает линейного ускорения CPU от потоков; общие БД, Ollama и GPU также
остаются ограниченными ресурсами.

Модель повторного ранжирования (CrossEncoder) теперь поддерживает CPU и CUDA.
GPU используется для поддерживаемых операций модели; регулярные выражения,
SQL, BM25 и управление очередью остаются на CPU. Выбор `auto` означает
«CUDA, если она доступна», а не перенос произвольной CPU-задачи при высокой загрузке.
В рабочем процессе используется одна модель; вызовы её inference защищены
от одновременного выделения десяти наборов GPU-буферов. При нехватке VRAM
размер пакета уменьшается, затем возможен переход на CPU с фиксацией причины.
Сам переход на CPU не гарантирует соблюдение лимита времени.

На RTX 4060 Laptop 8 ГБ память разделяют Ollama и reranker. Изменение профиля
не загружает десять копий модели и не меняет установленную модель Ollama.
Скачивание CUDA-зависимостей при первой сборке может занять заметное время.

## Уточнённая гипотеза B1

**При одинаковых ресурсах CPU/GPU и общем числе рабочих слотов, на каталоге
из 12 533 позиций и при одновременной фоновой подготовке каталога, разделение
интерактивных и пакетных задач с резервированием рабочих слотов уменьшает
p95 полного времени подбора не менее чем на 30% относительно общей очереди.
При этом скорость фоновой подготовки составляет не менее 90% baseline,
а доля неуспешных подборов — менее 1%. Проверка проводится при одинаковой
заранее заданной нагрузке от 10 активных учётных записей.**

Baseline — конфигурация с общей очередью. 30% — заранее выбранный инженерный
порог, а не универсальная величина из литературы. Сокращение времени до 70%
означает ускорение в 1/0,7 ≈ 1,43 раза. Для десятикратного ускорения необходимо
сократить время на 90%; из числа пользователей это не следует.

Три сравнения выполняются раздельно:

| Вопрос | Сравнение | Что фиксировать |
|---|---|---|
| Влияет ли разделение очередей? | shared против split с фоном | одинаковые CPU/GPU, число слотов, модели, входы, интенсивность и таймаут |
| Влияет ли число учётных записей? | один пользователь × 10 одновременно против десяти пользователей × 1 | одинаковая конфигурация и одни и те же десять потребностей |
| Ускоряет ли GPU? | parallel CPU против parallel GPU | одинаковые слоты, запросы, прогрев, алгоритмы и таймаут |

Сравнение последовательной серии с одновременной показывает эффект расписания
запросов. Это дополнительная диагностика, а не доказательство B1.
Если включить GPU и увеличить число слотов только в проверяемом варианте,
получится проверка совокупности изменений, а не изоляции очередей.

Профиль `parallel` намеренно не допускается к подтверждающей кампании B1:
у него другой вычислительный бюджет. После `restore shared` или `restore split`
доступны исходные два рабочих слота. Документированный ранее пересмотр
интенсивности подтверждающего протокола остаётся отдельной задачей:
в этой версии исходная полная кампания по-прежнему использует 20 запросов/мин.
Она может перегружать данный ноутбук; короткая диагностика не подтверждает гипотезу.

## Установка обновления с сохранением данных

Архив содержит исправление для версии 3.9.13-b1.1, выданной ранее вместе
с режимом «одна строка TXT = одна потребность». Скопируйте архив
`StockExpert_B1_parallel_GPU_patch.zip` в `/home/ganie/Downloads`.
Завершите текущие эксперименты. Затем в WSL:

```bash
mkdir -p /home/ganie/StockExpertB1_parallel_update
unzip -q -o /home/ganie/Downloads/StockExpert_B1_parallel_GPU_patch.zip -d /home/ganie/StockExpertB1_parallel_update
python3 /home/ganie/StockExpertB1_parallel_update/apply_update.py /home/ganie/StockExpertB1 --check
python3 /home/ganie/StockExpertB1_parallel_update/apply_update.py /home/ganie/StockExpertB1
cd /home/ganie/StockExpertB1
bash b1-parallel.sh start gpu 4
bash b1-parallel.sh gpu-check
```

Установщик проверяет исходные файлы, сохраняет резервную копию изменяемого
кода рядом с проектом и не заменяет `.env` или `b1-local.sh`.
При конфликте с вашей версией он перечислит файлы и остановится до записи.
Не обходите проверку массовым копированием поверх неизвестной версии.

Скрипт запуска обнаруживает существующие контейнеры, сеть и порты.
Он пересоздаёт только сервисы приложения с `--no-deps`; PostgreSQL,
Redis, MinIO, Qdrant, Ollama и их volumes сохраняются.
Если инфраструктура остановлена, сначала восстановите текущий штатный запуск.
При активных заданиях переключение блокируется до их завершения.
Команды удаления volumes не нужны.

На вашем стенде ожидается прежний интерфейс `http://localhost:5176`;
скрипт напечатает фактически найденный адрес. Обновите страницу через Ctrl+F5.

## Как проверить новый сценарий

1. Откройте сервисный раздел → «Проверка гипотезы B1».
2. Выберите готовую базу 12 533 позиции и сессию с десятью готовыми потребностями.
3. Выберите «1 пользователь × 10 запросов одновременно».
4. Для диагностики долгих операций можно установить лимит 600 с на запрос.
   По умолчанию сохранены 120 с. Увеличение лимита не ускоряет вычисления.
5. Дождитесь результата, скачайте JSON/CSV. Проверьте: отправлено 10,
   завершено 10, успешно 10, ошибок 0; затем сравните p95 и время всей серии.
6. Повторите «10 пользователей × 1 запрос одновременно» и последовательную
   серию при тех же слотах, прогреве и лимите. Между опытами дождитесь
   завершения серверных задач: клиентский таймаут сам по себе их не отменяет.
7. Повторяйте серии и фиксируйте CPU, RAM, VRAM и фактическое устройство
   reranker. Одна серия из десяти запросов даёт только предварительную диагностику.

Для разрешения до десяти одновременно активных подборов:

```bash
cd /home/ganie/StockExpertB1
bash b1-parallel.sh start gpu 10
```

Это лимит конкурентных задач, а не обещание одновременного выполнения всех
вычислений на GPU. При 16 ГБ системной памяти разумно сначала проверить четыре
слота: ранее на снимке уже было занято 96% RAM. Если десять слотов повышают
p95, вызывают ошибки или подкачку, вернитесь к четырём либо двум:

```bash
bash b1-parallel.sh start gpu 2
```

Проверка CUDA показывает доступность устройства внутри контейнера, но не
доказывает ускорение. Фактический выбор устройства/переход на CPU фиксируется
в логах и runtime задания. Для сопоставления с CPU при тех же четырёх слотах:

```bash
bash b1-parallel.sh start cpu 4
bash b1-parallel.sh status
bash b1-parallel.sh logs
```

Возврат к исходному бюджету B1:

```bash
bash b1-parallel.sh restore shared
```

Для раздельных очередей того же исходного бюджета — `restore split`.
При дальнейших переключениях используйте этот скрипт: он сохраняет выбранный
профиль и число слотов. Старый `b1-local.sh` не знает о новом профиле.

## Технические основания

- Celery 5.5.2: `solo` выполняет задачи последовательно; `threads` допускает
  конкурентные задачи в одном процессе. У альтернативных пулов есть ограничения,
  включая отсутствие части механизмов soft time limit; здесь сохраняются
  прикладной контроль статуса и явные HTTP-таймауты.
  https://docs.celeryq.dev/en/v5.5.2/userguide/concurrency/index.html
- Docker Compose: доступ к GPU требует резервирования устройства и настроенного
  Docker/NVIDIA окружения, одной настройки Python недостаточно.
  https://docs.docker.com/compose/how-tos/gpu-support/
- PyTorch 2.7.0 имеет отдельные сборки CPU и CUDA 12.6. Обновление использует
  выбираемый при сборке вариант; CPU остаётся стандартом старого профиля.
  https://pytorch.org/get-started/previous-versions/
