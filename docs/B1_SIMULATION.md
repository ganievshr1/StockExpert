# B1: дискретно-событийная модель организации очередей

**Это результаты некалиброванной имитационной модели. Скрипт не запускает
StockExpert, не отправляет HTTP-запросы и не измеряет реальную скорость LLM,
PostgreSQL, Redis или Qdrant. Все длительности ниже заданы как допущения.**

В конфигурации с непрерывным фоном модель **не подтверждает B1**: разделение очередей не
уменьшает p95 на 30%. При одной фоновой обработке каталога и двух workers
общая очередь уже оставляет один worker для подбора. Обе схемы ограничиваются
одним и тем же общим GPU-ресурсом. Это результат модели, а не отрицательный
результат нагрузочного испытания реального приложения.

## Что сравнивается

| Параметр | Baseline | Проверяемая схема |
|---|---|---|
| Очереди | Общая FIFO | Отдельные interactive и batch |
| Основной бюджет | 2 workers | 1 interactive + 1 batch |
| Чувствительность | 4 workers | 1 interactive + 3 batch |
| GPU | Общая FIFO, один одновременный вызов | Точно такой же общий ресурс |
| Дополнительная чувствительность | GPU-слотов столько же, сколько workers | Столько же слотов, сколько у baseline |
| Подготовка каталога | Один job занимает один worker до завершения | Один job занимает один batch-worker |
| Подбор | Один job занимает worker до завершения | Один job занимает interactive-worker |
| Перехват свободных ресурсов | Общий пул может брать любую работу | Work stealing отсутствует |

Реальная структура `stockexpert.run` исполняет порции нормализации внутри одного
задания. Поэтому модель не превращает 12 000 строк в 12 000 самостоятельных
Celery-задач. Такое превращение искусственно создало бы совсем другую FIFO-нагрузку.

Модель представляет один GPU-вызов на строку каталога. Между вызовами GPU
освобождается, а worker остаётся занятым каталогом. Внутренние thread pools,
пакетная векторизация, переключение моделей и actual GPU scheduling не моделируются.
Параметр `gpu_rows_per_call` позволяет явно исследовать более крупные вызовы.

## Данные и сценарии

Во всех сценариях подбор использует заранее готовую неизменяемую версию `ready_v0`
на **12 000 строк**. Содержимое настоящего ЕБДЗ скрипт не читает. При включённом фоне
один независимый job готовит новую версию `new_v1` того же размера. Она не
публикуется в середине поиска. В исходном исследовательском протоколе указано
12 533 строки; 12 000 здесь — явно выбранный размер текущей модели, его можно
заменить параметром `catalog_rows`.

1. `simultaneous_10`: десять разных условных аккаунтов отправляют по одному
   подбору одновременно. Это иллюстрация пользовательского сценария, десять
   наблюдений недостаточны для основного статистического вывода.
2. `sequential_10`: один условный аккаунт отправляет десять подборов, каждый
   следующий — после результата или дедлайна предыдущего. Это закрытая модель.
   Её пропускную способность нельзя выдавать за одинаковую с открытым потоком.
3. `full_protocol`: десять условных аккаунтов по кругу, один новый подбор каждые
   3 виртуальные секунды независимо от завершения предыдущего. Всего 600 подборов
   за окно 1 800 секунд. Это основной сценарий B1.

Каждый сценарий выполняется **без фона и с фоном**, при двух бюджетах workers и
двух вариантах доступности GPU. Для каждой комбинации сделано пять парных
прогонов; порядок baseline/variant чередуется. Для лёгкого профиля сохранено
**240 прогонов**. Дополнительно выполнены **20 прогонов тяжёлого профиля**:
полный протокол, 2 workers, один GPU-слот, пять пар без фона и пять пар с фоном.

Прогрев — 180 виртуальных секунд с таким же редким потоком запросов до измеряемого
окна. Он служит одинаковым начальным участком модели; это не реальная загрузка
весов или прогрев вычислительного устройства. Отсутствие отставания виртуального
генератора также не подтверждает производительность настоящего HTTP-генератора.

## Явные допущения о длительности

| Параметр | Значение по умолчанию | Значение для интерпретации |
|---|---:|---|
| CPU на одну строку каталога | 0,02 с | Произвольное среднее, не замер |
| GPU на одну строку каталога | 0,08 с | Произвольное среднее, не замер |
| CPU одного подбора | 0,10 с | Произвольное среднее, не замер |
| GPU одного подбора | 0,25 с | Произвольное среднее, не замер |
| Передача запроса | 0,01 с | Модельная постоянная |
| Регистрация запроса | 0,01 с | Модельная постоянная |
| Передача результата | 0,01 с | Модельная постоянная |
| Интервал polling | 0,25 с | Из принятого протокола |
| Дедлайн пользователя | 120 с | Из принятого протокола |
| Коэффициент вариации времени обслуживания | 0,20 | Логнормальное распределение с указанным средним |

Тяжёлый профиль задаётся файлом `experiments/b1_heavy_assumptions.json` и меняет
только среднее GPU-время строки каталога на **1,00 виртуальную секунду**. Это
отдельное условное допущение для продолжительной фоновой работы. Оно не является
оценкой скорости какой-либо LLM и не выбиралось для получения 30% выигрыша.

Случайные последовательности фиксированы seeds `20261107`–`20261111`. Одинаковые
работы в паре получают одинаковые длительности. Потоки случайных чисел для
прогрева, каталога и пользовательских запросов разделены: включение фона не
подменяет длительности самих подборов. В сравнении очередей не изменяются модели
обслуживания, общее число workers или GPU-слотов.

`gpu_slots = workers` — исследование отсутствия общего GPU-ограничения, а не
утверждение о наличии нескольких видеокарт у пользователя. Значения 2 и 4 workers
не описывают реальные выделенные CPU/RAM: память и конкуренция ОС здесь опущены.

## Метрики и решение по гипотезе

Полное клиентское время начинается при отправке задания и заканчивается при
наблюдении готового результата. Оно включает передачу и регистрацию, ожидание
worker, CPU, ожидание общего GPU, GPU, ожидание следующего polling и передачу
результата. Ответ о принятии задания не считается готовым подбором.

`p95` считается методом ближайшего ранга по успешным запросам. Рядом всегда
сохраняются число отправок, успехов и дедлайнов. Процентиль пустой выборки равен
`null`. Дедлайн не отменяет серверное задание: его последующее потребление
ресурсов остаётся в модели. Это допущение явно записано в manifest.

Скорость каталога — число уникальных завершённых строк **в одном и том же
30-минутном окне**, делённое на 30. Подборы/мин также считаются только в этом
окне. Наблюдение продолжается до `window_end + 120 s` для классификации дедлайнов;
завершения из этого хвоста не увеличивают оконную пропускную способность.
Дополнительно сохраняется полное время подготовки каталога, поскольку конечный
каталог может полностью закончиться в обоих вариантах и дать одинаковые
400 строк/мин за фиксированное окно, несмотря на различия времени его завершения.

Для каждой из пяти пар полного протокола с фоном проверяется одновременно:

- `p95_variant / p95_baseline <= 0.70`;
- `catalog_rate_variant / catalog_rate_baseline >= 0.90`;
- `variant_error_rate < 0.01`.

До проверки границ необходимо соблюсти условие: **один и тот же фоновый job
активен всё измеряемое окно**, в обеих конфигурациях, без замены закончившегося
каталога новым. Если он завершился раньше 1 800 секунд, пара получает статус
`INVALID_B1_BACKGROUND_COMPLETED_EARLY`. Лёгкий профиль сохраняется для контроля
и исследования поведения, но его полные прогоны с ранним завершением фона не
используются для принятия или отклонения основной B1.

Для интерпретации отношения процентилей введён явный дополнительный защитный
критерий: не менее 100 успешных наблюдений у каждой схемы и менее 1% ошибок
baseline. При его нарушении результат обозначается как неинтерпретируемый из-за
недостаточных наблюдений/цензурирования, а не как доказанное ускорение. Это
консервативное уточнение модели по сравнению с исходным текстом протокола.

Итоговый статус `B1_SUPPORTED_ONLY_WITHIN_MODEL` возможен только при выполнении
границ во всех пяти парах. Контрольные сценарии никогда не подтверждают B1.
Успешное завершение в модели означает только событие завершения. Корректность
выдачи МТР, права доступа и изоляция реальных пользователей не проверяются.

## Полученные модельные результаты

Лёгкий профиль, бюджет 2 workers, общий GPU с одним слотом. Ни одно число в таблице
не является измеренной характеристикой StockExpert.

| Сценарий | Фон | p95 baseline, диапазон пяти прогонов | p95 split, диапазон пяти прогонов |
|---|---|---:|---:|
| 10 пользователей × 1 подбор одновременно | Нет | 2,53–2,78 с | 3,53–3,78 с |
| 10 пользователей × 1 подбор одновременно | Да | 4,03–4,28 с | 4,03–4,28 с |
| 1 пользователь × 10 подборов последовательно | Нет | 0,53 с | 0,53 с |
| 1 пользователь × 10 подборов последовательно | Да | 0,53–0,78 с | 0,53–0,78 с |
| 600 подборов за 30 минут | Нет | 0,53 с | 0,53 с |
| 600 подборов за 30 минут | Да | 0,53 с | 0,53 с |

Для десяти запросов p95 ближайшего ранга совпадает с максимальным наблюдением.
Медиана времени выполнения всей десятки без фона: 2,78 с для одновременной
отправки через общий пул и 5,30 с для одного последовательного пользователя.
Медиана полной десятки — другая метрика, она не равна медиане времени одного
подбора. Запросы от разных пользователей могут обслуживаться параллельно,
но каждый из них может ждать дольше при одновременном поступлении.

Во всех пяти парах лёгкого профиля с фоном:

- отправлено и успешно завершено по 600 запросов у каждой схемы;
- отношение p95 = **1,00**, уменьшение на 30% не достигнуто;
- подготовлено 12 000 строк за измеряемое окно у каждой схемы;
- оконная скорость каталога = **400 строк/мин**, отношение скоростей = **1,00**;
- ошибка по дедлайну = **0%** в рамках модели;
- время завершения отдельного каталога составляет примерно 1 298–1 305
  виртуальных секунд при принятых допущениях.

Именно раннее завершение каталога делает эти пары **невалидными для полной B1**.
Отсутствие ускорения в них остаётся описательным результатом, а не основанием
принять или отклонить гипотезу при непрерывной фоновой работе.

Для основного вывода с непрерывным фоном выполнен тяжёлый профиль:

| Парный прогон | p95 baseline / split | Строк каталога за общее окно, baseline / split | Скорость каталога, baseline / split | Ошибки |
|---|---:|---:|---:|---:|
| 1 | 1,53 / 1,53 с | 1 621 / 1 621 | 54,03 / 54,03 строк/мин | 0% / 0% |
| 2 | 1,53 / 1,53 с | 1 633 / 1 633 | 54,43 / 54,43 строк/мин | 0% / 0% |
| 3 | 1,53 / 1,53 с | 1 622 / 1 622 | 54,07 / 54,07 строк/мин | 0% / 0% |
| 4 | 1,53 / 1,53 с | 1 631 / 1 631 | 54,37 / 54,37 строк/мин | 0% / 0% |
| 5 | 1,53 / 1,53 с | 1 637 / 1 637 | 54,57 / 54,57 строк/мин | 0% / 0% |

Все пять пар тяжёлого профиля валидны по условию непрерывной фоновой работы,
содержат по 600 успешных подборов для каждой политики. Отношения p95 и скорости
каталога равны 1,00. Критерий уменьшения p95 на 30% не выполнен. **B1 не
подтверждена в рамках этой модели при заданных допущениях.**

В лёгком профиле при чувствительности к 4 workers и при снятии общего
GPU-ограничения отношения p95 во всех парах равны 1,00. Эти пары также имеют
раннее завершение фона и не подтверждают полную B1. В контроле одновременных десяти запросов выделение лишь одного
interactive-worker может ухудшать задержку: зарезервированные batch-workers
простаивают. Модель намеренно допускает отрицательный результат для split.

Причина отсутствия выигрыша в основном опыте понятна из нагрузки: один долгий
каталог занимает один worker, а запрос каждые 3 секунды обслуживается быстрее
этого интервала. Общий пул уже обладает достаточным свободным worker. Эти
предпосылки нужно проверить реальными трассировками, прежде чем переносить вывод
на приложение. Несколько одновременно готовящихся каталогов, более длинные
подборы, крупные неделимые GPU-вызовы и burst-нагрузка могут менять результат;
они не объявляются испытанными сценарием этого запуска.

## Воспроизведение и результаты

Из корня проекта, Python 3.10 или новее, сторонние пакеты не требуются:

```bash
python experiments/b1_simulation.py --self-test
python experiments/b1_simulation.py
python experiments/b1_simulation.py --config-json experiments/b1_heavy_assumptions.json --workers 2 --gpu-modes one --scenarios full_protocol --output-dir experiments/results/b1_simulation_heavy
```

Для собственных явно названных допущений создайте JSON с полями `ModelConfig` и
передайте `--config-json`. Например, файл может содержать
`{"catalog_rows": 12533, "interactive_gpu_seconds": 1.0}`. Скрипт не подбирает
параметры автоматически и не пытается получить подтверждение гипотезы.

Более короткий отдельный запуск:

```bash
python experiments/b1_simulation.py --workers 2 --gpu-modes one --scenarios full_protocol --output-dir experiments/results/b1_single_gpu
```

| Файл | Содержание |
|---|---|
| `experiments/b1_simulation.py` | Модель, команды запуска и встроенные проверки |
| `experiments/results/b1_simulation/manifest.json` | Все параметры, seeds, версия Python, SHA-256 кода, допущения |
| `summary.json` | Все 240 прогонов, 120 парных сравнений и групповые выводы |
| `raw_jobs.jsonl`, `raw_jobs.csv` | 49 720 записей заданий с началом, ожиданием, завершением и исходом |
| `catalog_progress.csv` | Завершённые строки каждые 100 строк и граница измеряемого окна |
| `runs.csv` | Метрики каждого отдельного прогона |
| `comparison.csv` | Парные отношения, границы и решение по B1 |

В каталоге `experiments/results/b1_simulation_heavy/` находится такой же набор
файлов для 20 дополнительных прогонов и 12 010 записей заданий. Всего для двух
профилей сохранено 260 прогонов и 61 730 записей заданий.

Одиннадцать встроенных проверок охватывают дедлайны, отсутствие результата у пустой
выборки, полное время с polling, открытое поступление, последовательную работу,
одинаковые ресурсы, воспроизводимость seeds, одинаковые времена работ с фоном и
без фона, расчёт пропускной способности строго в общем окне и проверку
непрерывности фона. Они проверяют
реализацию модели, но не валидируют её допущения по реальной системе.

Для калибровки нужны серверные события `job_started`, `stage_finished`,
`job_completed`, GPU-очередь и клиентские времена реального стенда. До их
получения эту таблицу допустимо использовать только как **имитационный
эксперимент с указанными предположениями**.
