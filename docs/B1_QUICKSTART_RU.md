# Запуск StockExpert и проверка B1

Эта инструкция относится к полному архиву `StockExpert_B1_full.zip`, папке `Stock3.9.12` и добавленной проверке B1. Прежний путь Excel → потребность → подбор сохранён. Для нового стенда используются отдельные Docker project, сеть и порты, поэтому существующую установку можно оставить без изменений.

## Что потребуется

- Windows 11 с WSL Ubuntu и Docker Desktop с интеграцией WSL либо Linux с Docker Engine.
- Docker Compose v2, Python 3 и `unzip`.
- Для основного compose — NVIDIA GPU, доступная Docker. Проверьте `nvidia-smi` в WSL. Без GPU используйте описанный ниже CPU override.
- Место для моделей и Docker volumes. Первое скачивание и загрузка моделей занимает отдельное время и не входит в измерение.

На компьютере с 16 GB RAM и RTX 4060 Laptop 8 GB запускайте один эксперимент за раз. Два бизнес-исполнителя имеют по одному слоту; повышение этого числа или лимита GPU в одном из сравниваемых режимов сделает сравнение некорректным.

## Новая установка в WSL

Скопируйте архив в домашний каталог WSL, затем выполните:

```bash
mkdir -p ~/StockExpert_B1
unzip ~/StockExpert_B1_full.zip -d ~/StockExpert_B1
cd ~/StockExpert_B1/Stock3.9.12
bash b1.sh init
```

`init` создаёт `stockexpert-backend/.env` со случайными секретами. Если файл уже есть, он сохраняется. Откройте его локально и запишите `ADMIN_USERNAME` и `ADMIN_PASSWORD` для входа. Не отправляйте `.env` вместе с результатами.

Исходный генератор настроек выбирает Qwen3-8B. Чтобы использовать ранее выбранный Qwen2.5-7B Q5, до первого старта согласованно задайте в `.env`:

```dotenv
LLM_DEFAULT_PROFILE=qwen25-7b-q5
LLM_PROVIDER=ollama
LLM_MODEL=qwen2.5:7b-instruct-q5_K_M
```

В каждой паре baseline/variant должны быть одинаковые модель, эмбеддинг, включение reranker, способ нормализации и настройки таксономии. Изменение модели между режимами запрещает вывод об эффекте очередей.

Запустите baseline и загрузите модели:

```bash
bash b1.sh start shared
bash b1.sh models
bash b1.sh status
```

`models` загружает `bge-m3` и указанную в `.env` локальную LLM. При выборе внешнего генератора эмбеддинг всё равно нужен. CPU reranker при первом применении загружает свои веса; сделайте пробный подбор до основного измерения.

| Адрес | Назначение |
|---|---|
| http://localhost:5175 | Интерфейс StockExpert |
| http://localhost:8002/docs | Описание API |
| http://localhost:8002/health/live | Проверка доступности процесса API |
| http://localhost:9003 | Консоль MinIO |

Успех `/health/live` ещё не доказывает готовность модели или worker. Перед серией выполните один обычный подбор. Полная диагностика `/health/ready` требует авторизацию и также не заменяет пробную обработку.

## Если NVIDIA недоступна

CPU override требует Docker Compose **2.24.4 или новее**. Он снимает запрос NVIDIA-устройства и не меняет бюджет рабочих процессов:

```bash
export B1_CPU=1
bash b1.sh start shared
bash b1.sh models
```

Сохраняйте `B1_CPU=1` для дальнейших команд и обеих конфигураций. CPU-режим может существенно увеличить время LLM и эмбеддингов; сравнивать CPU baseline с GPU variant нельзя.

## Подготовка входов через прежний интерфейс

1. Войдите как администратор. Создайте сессию с вариантом **Загрузить новый Excel**.
2. В разделе **Данные сессии** загрузите каталог примерно на 12 000 позиций и **потребности в одну исходную сессию до нормализации**. Для одного TXT с десятью наименованиями выберите «Список позиций — одна строка = одна позиция». Также можно загрузить десять отдельных файлов, каждый с одной потребностью. Для проверки требуются 10 отдельных потребностей, а не 10 признаков одной потребности.
3. Выполните подготовку столбцов, проверьте соответствие, утвердите столбцы и нормализуйте данные. При включённой таксономии завершите и утвердите её. Дождитесь отсутствия активных заданий.
4. Убедитесь, что каталог появился в списке **Использовать готовую базу**, а в исходной сессии получено не менее 10 нормализованных паспортов потребностей. Эту сессию можно выбрать в B1 одновременно как готовую базу и источник потребностей. Если база уже подготовлена отдельно, создайте сессию с вариантом **Использовать готовую базу**, загрузите в неё один TXT в режиме списка либо десять отдельных файлов до нормализации и завершите обработку. При создании новой сессии выберите те же метод нормализации, модель и состояние H2, что использовались для готовой базы. Схема и категории потребностей должны совпадать с выбранной базой.
5. Сохраните неизменными Excel, эти 10 потребностей, способ нормализации и модель на всю серию. Пробный подбор должен завершаться с доступным результатом.

В поставке есть готовый синтетический комплект:

- `fixtures/B1_catalog_12000_SYNTHETIC.xlsx` — ровно 12 000 программно созданных описаний; лист `SYNTHETIC_12000`, заголовок в строке 1, наименование — только столбец B.
- `fixtures/requirements_10/Q01.txt` … `Q10.txt` — десять отдельных потребностей. Загрузите **все десять файлов в одну исходную сессию до нормализации**, либо используйте общий TXT в режиме построчного списка.
- `fixtures/B1_fixture_manifest.json` — состав и контрольные суммы; подробности в `fixtures/README.md`.

Общий `fixtures/B1_requirements_10_SYNTHETIC.txt` можно загрузить одним файлом в режиме «Список позиций — одна строка = одна позиция». В обычном режиме опросного листа такой список может быть распознан как одна потребность. В комплекте нет готовых паспортов — приложение получает их выбранным методом нормализации.

Сохранённые исходные примеры на 100 строк подходят для функциональной отладки. Синтетические 12 000 строк и имитационная модель явно помечены; результаты на них нельзя подписывать как измерение реальной ЕБДЗ или экспертную оценку качества.

## Два коротких сценария

Откройте **Для разработчика → Проверка гипотезы B1**, выберите готовую базу и сессию с 10 нормализованными потребностями.

| Сценарий | Что делает контроллер | Что сравниваем |
|---|---|---|
| 10 пользователей по одному подбору | Отправляет 10 запросов одновременно от разных тестовых аккаунтов | Задержку каждого подбора, p95, время всей серии, ошибки |
| 1 пользователь и 10 последовательных подборов | Следующий запрос отправляет после получения результата предыдущего | Те же показатели при последовательной подаче |

Тестовые аккаунты и отдельные сессии создаются автоматически внутри текущей организации. Копирование готовой базы и паспортов происходит до измеряемой серии. Короткие сценарии используют 10 копий сессии, полный протокол — пул из 50; это требует дополнительного места в PostgreSQL и MinIO и времени подготовки. Исходные пользовательские сессии не изменяются.

Если подготовка каталога полностью завершилась до этих 10 запросов и другой фоновой работы нет, это **диагностическая серия без фоновой нагрузки**. Она отвечает на вопрос о параллельном и последовательном использовании, но не подтверждает B1. p95 по 10 наблюдениям методом ближайшего ранга совпадает с максимальным наблюдением; для устойчивого вывода нужен полный протокол.

## Полная проверка гипотезы

Для подтверждающей кампании выберите полный протокол. Допускается ровно 12 000 или 12 533 доступные нормализованные позиции; фактическое число фиксируется в результате. Готовая база используется для поиска. Создайте ещё одну сессию как шаблон фоновой подготовки: загрузите тот же Excel и потребность, выполните подготовку и утвердите сопоставление столбцов. Число строк фонового каталога должно совпадать с готовой базой. Выберите эту отдельную сессию в поле **Фоновая обработка**. Контроллер готовит её копию, поэтому исходный шаблон сохраняется. Одна такая копия обрабатывается в фоне; изменение поисковой базы в середине измерения не допускается.

| Параметр | Значение |
|---|---|
| Учётные записи | 10 |
| Прогрев | 180 секунд |
| Измеряемое окно | 1800 секунд |
| Новый подбор | Каждые 3 секунды, независимо от завершения предыдущего |
| Число запланированных подборов | 600 за один прогон |
| Ожидание результата | 120 секунд на подбор |
| Опрос статуса | Через 250 мс |
| Повторы | 5 пар baseline/variant с чередованием порядка |
| Критерии каждой пары | `p95_split / p95_shared ≤ 0.70`, `V_split / V_shared ≥ 0.90`, ошибки split `< 1%` |

Пять пар содержат десять измеряемых прогонов. Только прогрев и окна занимают 5,5 часа, дополнительно требуется подготовка, завершение оставшихся заданий и переключение конфигураций. Если приложение не успевает выполнить запрос за 120 секунд, это отражается как неуспех; тайм-аут нельзя увеличивать после просмотра результата, сохраняя прежний критерий.

Когда кампания показывает ожидание другой конфигурации, дождитесь завершения активных задач. В терминале из корня проекта выполните требуемый вариант:

```bash
bash b1.sh start split
```

или верните baseline:

```bash
bash b1.sh start shared
```

Затем на вкладке B1 нажмите продолжение. Контроллер сам Docker не переключает. `b1.sh` блокирует перезапуск при активных бизнес- или лабораторных заданиях; не обходите эту проверку, очищая очередь Redis.

Не запускайте параллельно ручные подборы, лабораторию H1/H2/H3 или нормализацию вне кампании. Во время сравнения не удаляйте исходные сессии, не меняйте доступность складских позиций и не очищайте общую базу.

## Как читать результат

- p95 относится к полному пути от фактической отправки запроса на подбор до получения результата. Быстрые GET статуса не смешиваются с подбором.
- Ошибки, тайм-ауты и пропуски генератора показываются рядом с процентилями. p95 только успешных запросов сам по себе недостаточен.
- Скорость фоновой подготовки — число уникальных корректно обработанных строк в одном и том же окне, а не количество HTTP 202.
- Сохраняйте все парные результаты, конфигурацию, исходные события и контрольные суммы данных. Итоговое подтверждение требует выполнения всех границ на валидных прогонах.
- Отдельная очередь может не дать улучшения: общая GPU, размер пакетной задачи и доля свободных исполнителей влияют на результат. Отрицательный результат фиксируется без изменения порогов задним числом.

Используйте экспорт JSON/CSV/ZIP на вкладке B1. В архив входят входные данные, события запросов, выдача кандидатов, контрольные суммы и сведения о конфигурации. Подробные данные контроллера находятся в постоянном Docker volume `b1_artifacts`; удаление контейнера само по себе их не стирает.

Между прогонами контроллер освобождает объёмные промежуточные строки результатов **тестовых сессий B1** после архивирования. Сохраняются задания, аудит, времена, контрольные суммы и полученная выдача кандидатов в экспорте. Для архивированной тестовой истории обычный маршрут может возвращать HTTP 410; смотрите экспорт B1. Прежние пользовательские сессии и их отчёты эта очистка не затрагивает.

Для запуска тех же серверных сценариев из терминала предусмотрен `stockexpert-backend/scripts/b1_load.py`. Он запрашивает пароль скрытым вводом; пароли не требуется помещать в командную строку:

```bash
cd stockexpert-backend
.venv/bin/python scripts/b1_load.py --username markov_f config
.venv/bin/python scripts/b1_load.py --username markov_f create \
  --scenario concurrent_10 --base-session BASE_UUID \
  --requirements-session REQUIREMENTS_UUID
cd ..
```

Замените UUID идентификаторами из вашего стенда, а имя пользователя — значением из `.env`. Полная справка: `python3 stockexpert-backend/scripts/b1_load.py --help`. CLI и кнопка B1 управляют одним контроллером; это не второй независимый генератор нагрузки.

## Имитационная модель

Модель запускается отдельно от приложения:

```bash
python3 experiments/b1_simulation.py --self-test
python3 experiments/b1_simulation.py --output-dir experiments/results/b1_simulation
```

Фактическая команда, параметры, результаты и допущения приведены в `docs/B1_SIMULATION.md`. Это дискретно-событийный расчёт при заданных временах обслуживания, а не запуск LLM на производственной базе. Его выводы проверяют правдоподобие архитектурной гипотезы и помогают выбрать нагрузку для реального стенда.

## Проверки и обслуживание

Backend:

```bash
cd stockexpert-backend
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
cd ..
```

Frontend:

```bash
cd stockexpert-frontend
npm ci
npm test
npm run build
cd ..
```

Автоматические backend-тесты используют временную SQLite и контролируемые замены внешних сервисов. Они проверяют логику и контракты, но не доказывают производительность PostgreSQL/Redis/GPU в Docker. Результаты имитации и результаты реального приложения не объединяются в одну таблицу без указания типа опыта.

Отдельно проверяется блокировка перезапуска при активных заданиях и сохранение volumes в команде остановки:

```bash
python3 -m unittest discover -s tests -v
```

Эти проверки используют записывающую замену команды Docker и не запускают контейнеры.

Посмотреть сервисы и последние сообщения:

```bash
bash b1.sh status
bash b1.sh logs
```

Остановить только новый стенд, сохранив данные:

```bash
bash b1.sh stop
```

Не используйте `docker compose down -v` для сохранённой серии. Для обновления уже используемой установки сначала сделайте резервную копию PostgreSQL и объектов MinIO, сохраните `.env`, имя compose-проекта и volumes. Эта инструкция по умолчанию создаёт отдельный стенд, а не переносит прежние данные автоматически.
