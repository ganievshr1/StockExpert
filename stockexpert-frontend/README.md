## Адаптивное обновление · 2 октября 2026

Интерфейс автоматически перестраивается под ширину окна: телефон, планшет, ноутбук и большой монитор. Масштабирование браузера остаётся доступным.

- До 900 px меню становится горизонтальным и прокручивается; выбранный раздел автоматически появляется в видимой области. Смена темы и выход доступны на телефоне.
- Карточки, формы и кнопки переносятся; на узких телефонах показатели выводятся в одну колонку. На больших мониторах рабочая область использует доступную ширину.
- Таблицы сохраняют читаемую ширину столбцов. При переполнении внутри таблицы появляются горизонтальная и вертикальная прокрутка, заголовки столбцов закреплены. Область таблицы доступна через Tab и прокручивается клавишами со стрелками.
- Страница прокручивается по высоте; боковое меню на низком экране имеет отдельную прокрутку. Непомещающийся контент не скрывается принудительно.
- Диалоги ограничены высотой текущего окна (`dvh` с запасным `vh`) и прокручиваются. Учтены безопасные отступы мобильного экрана; увеличены кнопки и поля ввода.
- Полосы прокрутки используют цвета активной темы. На Android/iOS и системах с автоскрытием видимость бегунков зависит от настроек браузера/ОС; прокрутка жестами сохраняется.

Это обновление фронтенда совместимо с прежним API 3.7; миграции базы не нужны. Чтобы применить изменения, замените файлы фронтенда и пересоберите контейнер из этой папки:

```bash
docker compose up -d --build
```

При запуске без Docker выполните `npm ci` и `npm run build`; содержимое `dist/` включено в архив. Подробности проверки — в `VALIDATION.md`.

## Запуск

Сначала запустите бэкенд по его README. Для разработки нужен Node.js 22+:

```bash
npm ci
npm run dev
```

Откройте http://localhost:5173. Используйте `ADMIN_USERNAME` и `ADMIN_PASSWORD` из `.env` бэкенда. Общего встроенного пароля нет.

Vite передаёт `/api` и `/health` на `http://127.0.0.1:8000`. Для другого адреса скопируйте `.env.example` в `.env.local` и измените `BACKEND_PROXY_TARGET`. Переменные `VITE_*` входят в публичную сборку: ключи моделей в них не помещаются.

Для запуска через Docker после запуска парного бэкенда:

```bash
docker compose up -d --build
```

Фронтенд откроется на http://localhost:5173. Nginx передаёт API и SSE на `backend:8000` через общую сеть `stockexpert-network`, которую создаёт compose бэкенда. Для удалённого доступа настройте HTTPS на внешнем reverse proxy.

```bash
npm run test
npm run build
npm run preview
```

`build` проверяет TypeScript и создаёт `dist`. `preview` предназначен для локальной проверки сборки. Docker собирает исходники самостоятельно; зависимости зафиксированы в `package-lock.json`.

## Рабочий процесс: Excel + TXT

1. Создайте сессию и выберите доступную модель. Можно загрузить новую базу или использовать готовую нормализованную базу.
2. В «Данные сессии» загрузите складской Excel `.xlsx` и опросный лист `.txt`. Поддерживаются UTF-8, UTF-8 BOM, UTF-16 BOM, Windows-1251. Сохранены прежние форматы потребности PDF с текстовым слоем, DOCX и XLSX. Лимит файла — 20 MiB, Excel — 25 000 непустых строк, текст одного опросного листа — 12 000 символов. Превышение возвращает ошибку, данные не обрезаются молча.
3. Подготовьте структуру, проверьте листы, строку заголовка и столбцы описания. Укажите все столбцы с техническими характеристиками, например `A, C, D`. Утвердите столбцы.
4. Запустите нормализацию всех позиций. В «Классификатор» проверьте категории, признаки и правила сравнения; утвердите схему. Подбор запускается после утверждения.
5. В «Подбор запасов» сравните кандидатов с потребностью и сохраните закупочное решение. Для рекомендованной позиции доступно отдельное подтверждение использования: оно исключает всю позицию из доступной базы во всех связанных сессиях.
6. Проведите экспертную проверку по инструкции ниже. Скачайте отчёт PDF/XLSX с выбранными разделами; историю можно выгрузить в CSV.

До подготовки структуры можно просматривать, заменять и удалять входные файлы. Ошибка чтения нового файла сохраняет прежний файл. После начала обработки источники блокируются. Отмена, повтор неудачного задания, повторный подбор и очистка доступны в управлении сессией. Очистка требует подтверждения.

## Как получить все метрики качества

Закупочное решение и эталонная разметка качества — отдельные действия. Рекомендация кандидата сама по себе не создаёт эталон.

| Метрика | Действие эксперта | Когда значение остаётся «Не измерено» |
| --- | --- | --- |
| F1 извлечения | «Проверка качества» → «Параметры и категории»: проверить значения по источнику, исправить ошибки и явно отметить проверенные поля | Нет проверенных полей с ненулевым знаменателем |
| Accuracy категорий | Выбрать правильную категорию и отметить «Категория проверена» | Не проверена ни одна категория с определённым эталоном |
| Precision shortlist | «Подходит / не подходит»: оценить пары, вошедшие в shortlist | Ни одна пара shortlist не оценена |
| Recall@150 | Проверить **все пары** выбранной потребности, включая позиции вне shortlist; можно нажать «Проверять все пары этой потребности» | Нет полностью проверенной потребности с хотя бы одной подходящей парой |

Нажимайте «Сохранить и далее» после каждой оценки, затем «Завершить экспертную проверку». Метрики появятся на экране «Метрики» и в отчётах. Любая последующая правка снимает завершение; завершите проверку снова. Новый запуск подбора имеет собственную разметку.

«Нет данных» сохраняет `null` — эксперт подтверждает отсутствие значения в источнике. Неотмеченное поле не оценивается. «Не могу оценить» пропускает пару без новой оценки. В расчёте участвует проверенная выборка; Recall описывает пары данного запуска, а не нерассмотренную физическую базу. Если знаменатель равен нулю, искусственное значение не подставляется.

Новые категории и признаки можно добавить до утверждения схемы. Добавление категории не переклассифицирует готовые паспорта. Новый признак не создаёт отсутствующие значения в уже извлечённых паспортах: неизвестные значения требуют проверки. Перестроение таксономии из паспортов сбрасывает ручные изменения.

## Архитектура

- `src/pages` — экраны и композиция интерфейса.
- `src/features/session` — загрузка, сопоставление столбцов, создание и управление сессией.
- `src/components` — повторно используемые элементы, сравнение характеристик, окна и навигация.
- `src/services` — типизированные HTTP-клиенты, SSE, работа с классификатором; сетевые запросы не дублируются в компонентах.
- `src/state` — авторизация, выбранная сессия, прогресс и тема.
- `src/hooks/useResource.ts` — загрузка данных с защитой от устаревших ответов.
- `src/types` и `openapi.json` — контракт с сервером.

Палитры заданы CSS-переменными. Использованы SVG из макета и локально поставляемый Inter из npm-пакета; внешние запросы к Figma или Google Fonts при работе не нужны. Тема сохраняется между посещениями. JWT хранится в sessionStorage; «Запомнить меня» выбирает localStorage до истечения срока токена.

Права `admin`/`dmto_expert`/`buyer`, выбор Ollama/DeepSeek, повторное использование базы, общий учёт использования запасов, SSE с резервным polling и проверка цепочки аудита сохранены. Проверки и ограничения сборки описаны в `VALIDATION.md`.

## Удаление сессий (обновление 2 октября 2026)

В списке закупочных сессий добавлены «Удалить» в каждой строке и «Удалить все сессии» над таблицей. Открытую сессию также можно удалить через «Управление данными». Одиночное удаление требует подтверждения, массовое — ввода слова `УДАЛИТЬ`.

«Удалить все сессии» действует на все сессии текущей организации на момент запроса, независимо от поиска, статуса, периода и текущей страницы. Сессии, созданные параллельно после начала запроса, в этот список не входят. Права соответствуют редактированию: `admin`, `dmto_expert`, `buyer`. Доступ к другой организации закрыт.

Удаляются запись сессии, исходники Excel/TXT, сохранённые отчёты, векторный индекс, паспорта, результаты, задания, метрики и аудит. Общие запасы, на которые ссылаются оставшиеся сессии, сохраняются. Записи об уже использованных позициях остаются в складском учёте со статусом `USED`: удаление сессии не возвращает их в доступный остаток. Файлы, ранее скачанные на компьютер, не удаляются.

При активных заданиях (`QUEUED`, `RUNNING`, `CANCEL_REQUESTED`) сервер возвращает 409: остановите обработку и дождитесь её завершения. Если внешний сервис недоступен, сессия остаётся в `CLEANUP_FAILED`, новые изменения блокируются, удаление можно повторить. Массовое удаление не является общей транзакцией: успешные удаления сохраняются, оставшиеся сессии и причины ошибок показаны в окне подтверждения.

После удаления обновляются список и счётчики, при необходимости выбирается предыдущая страница. Если удалена открытая сессия, её выбор сбрасывается и открывается рабочий стол. Схема БД не меняется.
